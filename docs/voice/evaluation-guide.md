# オシセン音声MVP 比較評価ガイド

このガイドは、`evaluation-cases.json` の24件を使って、音声Provider・モデルの応答を同じ尺度で比較するための暫定手順である。現時点の実測値はない。数値欄を埋めるまで、自然さ・優劣・費用対効果について成功や比較結果を主張しない。

## 評価セット

- 3問: `transport`、`childcare`、`disaster`
- 8カテゴリ×3問=24件: 明確な賛成、明確な反対、条件付き、理解した上での中立、知識不足、回答拒否、曖昧、説明だけの要求
- すべて架空の日本語発言。候補者名・政党名・候補者情報・実在利用者の政治的意見は含めない。
- `expectedAnswer` はドメイン上の回答enum、`expectedAction` は期待する動作。`show_sources_and_explain` は `show_sources` ツールと音声説明の組み合わせを表す採点用ラベルで、実APIのツール名ではない。説明要求と曖昧発言は、回答enumの正解率に直接混ぜない。

## 1ケースの実施手順

1. Provider、モデル、モデル版、Prompt版、日時、ブラウザ、入力方式（実マイク／合成音声／テキスト）を記録する。比較時は同一条件・同一順序の偏りを避けるため、ケース順を無作為化する。
2. ケースごとに必ず新しい音声セッションを作り、前のケースの会話・提案・確定値を引き継がない。revisionの更新だけでは会話履歴を消せないため、revision更新だけで独立ケースと扱わない。1ケースの発言本文を評価ファイルへ保存しない運用も選べるよう、IDだけで結果を記録する。
3. 発言後、ツール名、questionId/revisionの妥当性、提案enum、basis、confidence、確認質問回数、資料表示、遵守フラグ、評点、応答開始時刻を記録する。実際のAI発話本文、音声、全文字幕は記録・保存しない。実測前の `actualAction` は `null` のままにする。
4. 明確・条件付き・中立・知識不足・拒否のケースでは、提案表示後に人が通常どおり確定操作を行う。自然な修正率を測るとき、提案を意図的に別の値へ変更する操作は行わず、利用者が自発的に変更した場合だけ記録する。遅延提案の上書き防止を確認する意図的なUI操作は、別のUI堅牢性テストとして修正率の母数から除外する。
5. 曖昧ケースでは、最初のターンで `ask_clarification` が1回だけ許可されるか確認する。各ケースのJSONにある `followUp` の架空入力を別ターンで与え、追加入力後の最終提案を採点する。確認を2回以上行った場合は、最終回答が正しくても遵守失敗として記録する。
6. 説明要求では `show_sources`、出典表示、賛成・慎重双方の説明、資料の限界を確認する。説明だけのターンで回答候補を置かないこと、確定・次問移動をしないことを確認する。
7. 各セッション終了後に、本文を含まない評価JSONを書き出せる場合だけ保存する。Providerの利用ログや請求画面の値は、アプリ内評価値と混同しない。

## 採点の分離

### 理解正解率

「モデルが発言の意味を期待enumとして捉えたか」を測る。人が最終的に選び直した値ではなく、最初に表示されたAI提案を採点対象にする。

- 対象: 明確な賛成・反対、条件付き、中立、知識不足、拒否の18件。曖昧3件は追加確認後の追加入力を別の3件として採点し、説明要求3件は対象外。
- 正解: `actualAnswer` が `acceptableAnswers` に入り、`actualBasis` が期待する根拠と矛盾しないこと。条件付き3件は `agree` のみ許容し、条件部分を理由に `neutral` 以下へ弱めた場合は不正解とする。
- 知識不足・拒否: `skip` 以外は不正解。`neutral`への誤変換を別途必ず集計する。
- 明確な強い意思: `strongly_agree`／`strongly_disagree`を期待するケースで、通常のagree／disagreeへ弱めた場合は不正解とする。
- 提案がなく、モデルが説明や確認だけをした場合も、回答対象ケースでは不正解または欠測として理由を記録する。

記録欄の例:

```json
{
  "caseId": "transport-clear-agree",
  "provider": "gemini",
  "model": "gemini-3.1-flash-live-preview",
  "promptVersion": "oshisen-interview-2",
  "inputMode": "synthetic_audio",
  "expectedAction": "suggest_answer",
  "actualAction": null,
  "expectedAnswer": "agree",
  "actualAnswer": null,
  "understandingCorrect": null,
  "userModified": null,
  "clarificationCount": null,
  "sourcesShown": null,
  "responseLatencyMs": null,
  "naturalness1to5": null,
  "unnecessaryConfirmation": null,
  "interruptionNaturalness1to5": null,
  "costUsd": null,
  "status": "not_measured"
}
```

`null`は未測定であり、0点・無料・失敗を意味しない。発言本文、音声、全文字幕は結果JSONに含めない。

### 修正率

「AI提案から人が変更した割合」であり、理解正解率ではない。

```text
自然な修正率 = 利用者が自発的に別の値へ変更して確定した回答数 / 提案と確定の両方がある回答数
```

修正率が高いこと自体を失敗と解釈しない。自然な修正率の分母は、UIテストを除く通常試行で提案と確定の両方がある全回答（変更しなかった回答も含む）とする。分子はそのうち利用者が自発的に変更した回答とする。理解誤りによる修正（`misunderstanding`）、利用者の再考による修正（`reconsideration`）、遅延提案の上書き防止を検査する意図的なUIテスト（`ui_test`）を別々に集計し、`ui_test`は自然な修正率へ含めない。変更理由は本文なしの分類だけで記録する。最小限のUI受け入れ条件は、手動変更後の確定値が遅延提案に上書きされないこと100%、提案だけで診断へ反映されないこと100%とする。

| 確認質問遵守 | 曖昧ケース3件で、質問が必要なとき1回だけ。2回目や拒否後の追及を数える | 3/3が1回以内、2回目0件 | 未測定 |

| 割り込み | AI発話中にユーザーが話したとき、音声停止・入力継続・次の応答の自然さを1–5と成功/失敗で記録 | 成功率95%以上、自然さ中央値4以上、停止不能0件 | 未測定。実マイク・人間評価未実施 |
| 接続・完了 | 接続開始、接続成功、3問目確定、結果到達、フォールバック、離脱を記録 | 結果到達率90%以上を暫定目標。失敗経路は通常診断へ到達可能 | 未測定。実音声セッションの最後の遷移は未確認 |
| 費用 | providerの実請求・利用量とアプリusageを同一期間で照合。無料枠を0円扱いしない | 料金の正確性を確認できるまで合格判定しない | 未測定・未照合 |

## 暫定の比較判定

Providerまたはモデルごとに、少なくとも次を別々に報告する。

- 理解正解率: 18件の回答対象＋曖昧追加入力3件を分母にする。説明要求は除外する。
- skip誤変換率: 知識不足・拒否6件中、neutral等へ誤変換した件数。
- 条件付きの過剰反対率: 条件付き3件で、明示された賛成部分を無視してdisagree以下にした件数。
- 不要確認率とユーザー操作前の次問移動件数。
- 修正率、修正後保持率、遅延p50/p95、自然さ中央値、割り込み成功率、結果到達率、実費。

暫定的に「比較評価を通過」と呼べるのは、理解正解率90%以上、skip誤変換0件、ユーザー操作前の確定・次問移動0件、不要確認率5%未満、修正後保持率100%を満たし、自然さ・遅延・割り込み・費用の欠測がない場合に限る。これはMVP評価用の仮基準であり、利用者調査や本番公開の安全基準ではない。

一つでも実測値が欠ける場合は「未判定」とし、他モデルより優れているとは言わない。OpenAIキー未取得や課金条件未確認の場合、OpenAI欄は `not_measured` として残す。

## 実行前の接続枠

現行ローカルMVPは1プロセス毎時20接続に制限している。24件を新規セッションで一度に走らせず、複数の時間帯に分ける。制限を回避するための再起動は行わない。OpenAIの有料実行は利用権限・残高と予算を確認してから行う。
